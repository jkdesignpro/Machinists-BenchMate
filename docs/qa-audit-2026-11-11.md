# QA audit, 2026-11-11

Independent check of Machinists BenchMate on branch `claude/scaffold-core` (commit `05e3210`), done on branch `claude/qa-audit`. I set out to find errors, not to confirm the work. Every value below was read from the running web app in headless Chromium through Playwright, not from the Rust tests. Each expected value was worked out independently, from first principles or from a well-known standard relation, or fetched from the source the app cites.

## Summary

- **Sample:** 134 checked outputs across every tool group (rows 1 to 132 plus the two fixed findings). Inputs came from Python `random` with **seed 20261111** (generic tools) and seed 20261112 (custom tools); edge cases and warning checks were added by hand. 29 data rows were checked against the cited public source, fetched live: 13 drill sizes, 8 Morse tapers, 2 NPT sizes and 6 hardness table rows.
- **Verdicts:** 122 OK, 0 WRONG, 9 MISLEADING, 3 UNVERIFIABLE. MISLEADING rows: 6, 14, 105, 106, 113, 114, 127 and the two fixed findings. UNVERIFIABLE rows: 128, 130, 131.
- **No wrong number was found** in any calculator, G-code program, DXF file or data row. All 29 data rows checked against their cited source (drill sizes, Morse tapers, NPT, hardness) match.
- **Fixed (2):**
  - The drill chart search for `#7` (the search box's own example) listed 217 sizes instead of drill #7.
  - In Material equivalents, 30 designations that publishers do print were also listed as "unsourced", with a tooltip saying "Not printed by any source yet".

  Both fixes come with a regression check in `tests/smoke/smoke.mjs`. That check failed before the fix and passes after it.
- **Left for the owner (7 MISLEADING, 3 UNVERIFIABLE):**
  - Tool-life cost per part leaves out the tool-change downtime cost, so the shown "lowest cost" tool life does not minimise the shown cost.
  - Theoretical Ra in µm is shown to 1 decimal place.
  - The Morse "angle" is the included angle but is not labelled so.
  - The G76/G92 infeed table can have a last roughing pass smaller than the minimum cut, which breaks the tool's own stated rule.
  - The taper tool gives no message when the small diameter is entered larger than the large one.
  - Knurl shows the same blank twice when the tooth count is exact.
  - µm vs um labels are inconsistent.
  - The UNVERIFIABLE items are listed under the findings.
- **After the fixes:** `cargo test` passes (160 tests). The full Playwright smoke pass passes: 89 tools open in inch and mm with no console errors, and the 2 new checks pass.

## Method

1. `bash scripts/build-web.sh` and `cargo test` (160 passed). Served `app/` with `python3 -m http.server`.
2. Drove the UI with Playwright in Chromium. For field-based tools I filled the inputs and read the results table. For custom screens I filled controls and read `#main` text. DXF files were downloaded through the browser.
3. Expected values come from my own calculations (Python), or from standard relations I know independently:
   - ISO 68-1 / ISO 965-1 thread formulas
   - ASME B1.20.1 NPT formulas
   - ISO 286 IT and fundamental-deviation values
   - Gilbert tool economics
   - the Taylor equation
   - cantilever beam deflection
   - chip-thinning geometry
   - circle and triangle geometry
4. Data rows were checked against the pages the app cites, fetched on 2026-11-11:
   - [Wikipedia, Drill bit sizes](https://en.wikipedia.org/wiki/Drill_bit_sizes)
   - [Wikipedia, Machine taper](https://en.wikipedia.org/wiki/Machine_taper)
   - [Wikipedia, National pipe thread](https://en.wikipedia.org/wiki/National_pipe_thread)
   - [Optimas, Hardness conversion table (ISO 18265)](https://optimas.com/technical-resources/hardness-conversion-table/)

   The shared web-fetch budget ran out repeatedly, so other data rows were checked against values I know independently. Those rows are marked "own" in the tables below. Nothing was copied from published handbooks or from Ultra.
5. DXF output was read back with ezdxf 1.4.5 in a separate environment. The checks were: strict `readfile`, audit, and hole positions, outline areas and extents recomputed by my own script.

## Samples

Verdict key:
- **OK:** within display rounding of the expected value.
- **WRONG:** the number is wrong.
- **MISLEADING:** the number is right but the display, label, rounding or rule could mislead.
- **UNVERIFIABLE:** I could not get an independent value.

## Findings

### Fixed (clear bugs, each with a regression check)

**F7. The drill chart search for a number size returned unrelated sizes** (`app/refdata.js`, drill chart `draw()`).
- The search box suggests "#7". The code stripped the `#` and then matched "7" anywhere in a name, a decimal inch value or an mm value, so `#7` listed 217 sizes, starting with #97.
- **Fix:** a query of the form `#<digits>` now matches that number drill exactly. Other searches are unchanged.
- **Test:** `tests/smoke/smoke.mjs` types `#7` and requires exactly one row, `#7`. Before the fix this check failed ("got 217 rows"); now it passes.

**F8. Material designations printed by publishers were also shown as "unsourced"** (`scripts/build_materials.py`, so also `data/materials.json`).
- The evidence files list some designations under `unsourced` even though a publisher prints them. The UI then showed, for example, "EN19 3" (three publishers) and right under it "EN19 unsourced", with the tooltip "Not printed by any source yet". That happened in 30 cells across 19 grades.
- **Fix:** the build drops an `unsourced` entry when it equals, under the build's own `norm()`, a value that a publisher prints in the same field. No printed value or evidence record was changed.
- **Test:** `tests/smoke/smoke.mjs` loads `app/data/materials.json` and fails if any unsourced designation equals a printed one. Before the fix it reported 30 problems; now there are none.

### For the owner (not changed)

**F1. Tool life: cost per part leaves out tool-change downtime** (MISLEADING; `core/src/lib.rs` `cost_per_part`, `app/tools.js` toollife).
- The lowest-cost tool life uses Gilbert's T = (1/n - 1)(Ct/Cm + tc), which comes from a cost per part that includes Cm x tc x tm/T. The displayed cost per part is cycle x Cm + Ct x tm/T + material, which leaves that term out.
- With the defaults (V 191, n 0.25, C 400, tc 2 min, 60/h), the tool shows 3.52 per part where the model it cites gives 3.73.
- Also, the "tool life for lowest cost" (21 min) does not minimise the cost function that is displayed.
- **Proposed fix:** `cost = cycle x Cm + (Ct + Cm x tc) x tm/T + material`. Alternatively, state in the label that tool-change time must already be included in the cycle time. Update the test at `core/src/lib.rs:682`.

**F2. Theoretical Ra and Rt in µm are shown to 1 decimal place** (MISLEADING; `app/tools.js` finish calc, `R(..., u, 1)`).
- With f 0.092 mm/rev and r 0.8 mm, Ra is 0.33 µm but shows as "0.3", a 10 % understatement. Fine finishes of 0.2 to 0.8 µm are exactly where this tool is used.
- **Proposed fix:** 2 dp in mm mode (keep 1 dp in µin).

**F3. The Morse taper "angle" is the included angle, but the label just says "angle"** (MISLEADING; `app/refdata2.js:141`).
- MT0 shows "angle 2.9816 deg". The cited Wikipedia table prints 1° 29' 27" (1.4908°, the half angle) in its "K" column. A user comparing the two, or setting a compound slide, can be off by a factor of 2.
- **Proposed fix:** label it "included angle", or show both included and half angle.

**F4. The thread infeed can make a last roughing pass smaller than the minimum cut** (MISLEADING; `core/src/cycles.rs` `infeed_by_first_cut`).
- The doc comment and the screen note both say each increment is at least the minimum cut. But the last roughing pass is clamped to `total - finish` with no check.
  - 1/2-13 G76: pass 19 is 0.0012 in against a minimum of 0.002.
  - M10 x 1.5 G92: pass 14 is 0.020 mm against a minimum of 0.05.
- For G76 the control plans its own passes, so this only affects the displayed table. For G92 the program really cuts that 0.02 mm rubbing pass.
- **Proposed fix:** merge a remainder under `min_cut` into the pass before, as `infeed_constant_depth` already does. Alternatively, correct the stated rule.

**F5. The taper tool shows "Enter the values above" when the small diameter is entered larger than the large one** (MISLEADING, minor; `app/tools.js` taper).
- **Proposed fix:** swap the two values, or say "Large diameter must be larger than the small diameter". The lathe taper program already handles either order.

**F6. Knurl: an exact whole tooth count lists the same blank twice** (cosmetic; `app/refdata3.js` knurl).
- Example: 96 DP on 0.750 in gives 72 teeth exactly, shown as "Blank for 72 teeth ... smaller" and "Blank for 72 teeth ... larger".
- **Proposed fix:** show one row, "exact: 72 teeth".

**F9. Units are spelt inconsistently** (cosmetic).
- Results tables use "um" and "uin" (Surface finish, Ball cusp, Fits, Surface texture). Material properties and Temperature compensation use "µm".
- **Proposed fix:** use µm and µin everywhere.

**U1. Insert tolerance class M** shows d ±0.05-0.152 mm and m ±0.08-0.202 mm, from one source (Walter). ISO 1832 is usually quoted as ±0.05-0.15 / ±0.08-0.20. The 0.152 and 0.202 look like conversions from inch (±0.006 and ±0.008 in). The cited Walter PDF could not be fetched (web-fetch budget ran out), so I could not confirm this is what Walter prints. Do not change the value; check the PDF.

**U2. G/M codes, Fanuc lathe G-code system C:** the app reports one third-party table that gives G21 for the threading cycle in system C. My understanding is that systems B and C both use G78. The app already marks this as a single source; a second source should be added.

**U3. Material 4140, GB column:** "40CrMoA" comes from one publisher. 42CrMo is the GB grade usually paired with 4140/42CrMo4. The value is shown with count 1 and a note; a second source should be added.

Other observations, not counted:
- Milling feed and Lathe feed do not back-calculate rpm from a known feed per minute when the rpm is blank. The labels ("Or known table feed") may suggest they do.
- The FCF builder's default tolerance is 0.25 in both unit systems, which is large for an inch frame.
